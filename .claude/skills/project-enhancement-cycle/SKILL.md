# 🔄 Project Enhancement Cycle

프로젝트를 지속적으로 개선하는 자동화 워크플로우입니다.

## 🎯 목표

```
코드베이스 건강도 → 이슈 발견 → 해결 → 문서 정리 → 반복
(새 이슈가 없을 때까지)
```

## 📋 작동 흐름

### 사이클 1
```
1️⃣ audit-to-issues
   코드베이스 점검 → 이슈 #1, #2, #3 등록
   
2️⃣ issues-plan-and-resolve  
   이슈 #1, #2, #3 해결
   
3️⃣ docs-audit
   문서 정리 (현황 반영, 중복 제거)
   
4️⃣ 체크: 새 이슈가 있는가?
   → YES: 다시 1️⃣으로
   → NO: 완료 ✅
```

### 사이클 2 (새 이슈 발견됨)
```
1️⃣ audit-to-issues (재실행)
   이전 개선 이후 남은 이슈 발견
   
2️⃣ issues-plan-and-resolve
   새 이슈 해결
   
3️⃣ docs-audit
   문서 재정리
   
... (반복)
```

## 🔁 순환 원리

### 각 단계의 역할

| 단계 | 스킬 | 목적 | 결과 |
|------|------|------|------|
| **감시** | audit-to-issues | 버그/개선사항 발견 | 이슈 등록 |
| **해결** | issues-plan-and-resolve | 이슈 계획 및 처리 | 이슈 닫힘 |
| **정리** | docs-audit | 문서 정확화 | 현황 반영 |
| **재감시** | audit-to-issues | 새 문제 발견 | 새 이슈 등록 or 완료 |

### 종료 조건

```
audit-to-issues 실행 후:
  - 새로운 이슈가 등록됨 → 계속 진행
  - 이슈가 등록되지 않음 → 사이클 종료 ✅
```

## 📊 상태 추적

### 각 사이클의 진행 상황

```
Cycle 1:
  ✅ audit-to-issues    → Issue #1, #2, #3 등록
  ✅ issues-plan-and-resolve → #1, #2, #3 해결
  ✅ docs-audit         → 문서 정리
  ✅ audit-to-issues    → 새 이슈 #4, #5 발견

Cycle 2:
  ✅ issues-plan-and-resolve → #4, #5 해결
  ✅ docs-audit         → 문서 재정리
  ✅ audit-to-issues    → 새 이슈 없음
  🎉 사이클 완료

최종:
  Total Issues Resolved: 5
  Documentation: Up-to-date
  Code Quality: Improved
```

## 🛠️ 프로세스 상세

### Step 1: audit-to-issues 실행
```bash
사용자: "프로젝트 개선 사이클"
↓
audit-to-issues 스킬 호출
  - 코드베이스 전체 감시
  - 버그, 보안 이슈, 개선사항 파악
  - GitHub 이슈 자동 등록
↓
결과: 새 이슈 목록 수집
```

**종료 조건 확인:**
- 새 이슈가 등록되었는가? → Step 2로 진행
- 이슈가 없는가? → 사이클 완료 🎉

### Step 2: issues-plan-and-resolve 실행 (이슈가 있을 때만)
```bash
issues-plan-and-resolve 스킬 호출
  - 이슈 분석 및 계획
  - 자동 또는 반자동 해결
  - 이슈 닫기
↓
결과: 모든 이슈 해결
```

### Step 3: docs-audit 실행
```bash
docs-audit 스킬 호출
  - 문서 점검
  - 현황 반영
  - 중복 제거
  - 자동 커밋
↓
결과: 문서 최신화
```

### Step 4: 반복 결정
```bash
audit-to-issues 스킬 재실행
  - 이전 개선 이후 남은 문제 감시
↓
새 이슈 발견?
  ├─ YES → Step 2로 (Cycle 반복)
  └─ NO → 완료 ✅
```

## 🎛️ 옵션

### 1. 최대 사이클 수 제한
```bash
"프로젝트 개선 사이클 (최대 3회)"
```
- 무한 반복 방지
- 리소스 제한 설정

### 2. 특정 영역만 감시
```bash
"프로젝트 개선 사이클 (보안만)"
"프로젝트 개선 사이클 (타입 체크만)"
```

### 3. 수동 검증 모드
```bash
"프로젝트 개선 사이클 (수동 승인)"
```
- 각 이슈 해결 전 사용자 승인
- 보수적인 접근

## 📈 기대 효과

```
사이클 진행:
  ✅ 버그 자동 발견 및 해결
  ✅ 문서 항상 최신 상태 유지
  ✅ 코드 품질 지속적 개선
  ✅ 팀원들이 일관된 프로세스 사용

장기 효과:
  ✅ 프로젝트 건강도 점진적 향상
  ✅ 기술 부채 감소
  ✅ 팀 생산성 증가
  ✅ 버그 조기 발견율 증가
```

## ⏱️ 실행 시간

```
사이클 1회:
  - audit-to-issues:    5-10분
  - issues-plan-and-resolve: 10-30분 (이슈 수에 따라)
  - docs-audit:         2-5분
  ────────────────────
  Total:               20-45분/cycle

예상 총 시간:
  - 3 cycles: 60-135분
  - 자동화로 인해 실제는 더 짧음
```

## 🔐 안전 장치

```
✅ 각 단계마다 이슈 체크
✅ 무한 루프 방지 (최대 사이클 수)
✅ 실패 시 중단 및 보고
✅ 모든 변경사항 git으로 기록
```

## 📝 커밋 메시지

각 단계 완료 후 자동 커밋:
```
1️⃣ audit-to-issues:
   "chore: 자동 점검으로 이슈 등록 (#1, #2, ...)"

2️⃣ issues-plan-and-resolve:
   "chore: 자동 해결된 이슈들 (#1, #2, ...)"

3️⃣ docs-audit:
   "docs: 사이클 #N 후 문서 정리"

전체:
   "chore: 프로젝트 개선 사이클 #N 완료"
```

## 🎯 사용 시나리오

### 시나리오 1: 정기적 유지보수
```
매주 월요일 아침:
"프로젝트 개선 사이클"
→ 주간 버그 자동 발견 및 해결
→ 문서 최신화
```

### 시나리오 2: Phase 완료 후 정리
```
Phase 1 구현 완료
"프로젝트 개선 사이클"
→ 모든 버그 정리
→ 문서 완벽화
→ Phase 2 시작 준비
```

### 시나리오 3: 리팩토링 후
```
대규모 리팩토링 완료
"프로젝트 개선 사이클"
→ 리팩토링으로 인한 버그 발견 및 해결
→ 코드 품질 검증
→ 문서 동기화
```
