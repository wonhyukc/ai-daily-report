## 계층 2 — 정성 (40점): 앵커 기반 채점, 증거 인용 필수

각 차원 8점. **`파일:라인` 또는 리포트 실물 증거 2개 이상 인용 없는 점수는 무효.**

### Q1. 테스트의 의미성 — "테스트가 진짜 회귀를 잡는가"

채점 절차: `git log --oneline --grep="fix"`에서 장애 수정 커밋 3개를 골라, 같은 버그가 재발하면 실패할 테스트가 존재하는지 추적.

| 점수 | 앵커 |
|------|------|
| 8 | 행동(behavior) 검증 + 경계 조건·실패 경로 포함. 과거 장애 3건 모두 재발 시 잡는 테스트 존재 |
| 6 | 행동 중심이나 핵심 경로 1곳 테스트 공백 (예: 수집 0건 시나리오) |
| 4 | happy path 위주. 구현 세부사항에 결합된 테스트 존재 (리팩토링하면 깨짐) |
| 2 | assert가 약하거나 mock이 실제 동작을 가림 — 통과를 위한 테스트 |

### Q2. 코드의 의도 표현력 — "처음 보는 사람이 이해할 수 있는가"

채점 절차: `git log --since="30 days ago" --name-only --pretty=""`로 최근 변경 상위 3개 모듈을 선정해 정독.

| 점수 | 앵커 |
|------|------|
| 8 | 이름만으로 의도가 읽힘. 주석은 "왜"만 설명. 함수가 한 가지 일만 함 |
| 6 | 대체로 명확하나 긴 함수(50줄+)·모호한 이름이 모듈당 1–2곳 |
| 4 | 호출부를 따라가야 이해되는 코드 다수. 죽은 코드·미사용 파라미터 존재 |
| 2 | 이름과 실제 동작이 불일치하는 곳 존재 |

### Q3. 실패 시나리오의 사려깊음 — "예상 밖 상황에서 어떻게 무너지는가"

채점 절차: collectors/processors의 예외 경로를 추적하고, "RSS 2개가 동시에 죽으면 내일 리포트는?"을 코드로 검증.

| 점수 | 앵커 |
|------|------|
| 8 | 외부 의존별 의도된 저하 전략 존재: 부분 실패 시 나머지로 생성, 전멸 시 명시적 알림. 로그로 원인 추적 가능 |
| 6 | 실패 처리는 있으나 전략 비일관 (수집기마다 재시도/포기 제각각) |

## 종합 등급

| 총점 | 해석 | 후속 행동 |
|------|------|----------|
| 90+ | 우수 | 유지 모드 — 이슈화 없음 |
| 75–89 | 양호 | 감점 항목만 이슈화 |
| 60–74 | 주의 | 낮은 계층부터 개선 사이클 가동 |
| <60 | 위험 | 운영 신뢰성(M4–M6)부터 즉시 복구 |

**안전장치**: 정성 차원에 2점이 하나라도 있으면 총점과 무관하게 이슈화. 정량 만점이 정성 결함을 가리지 못하게 한다.

**추이 규칙**: 정성 점수는 전회 대비 변화로 해석. ±2점 이내 변동은 노이즈로 간주하고 이슈화하지 않는다.
