# Issues Plan & Resolve — 이슈 계획 수립 후 일괄 처리

## Overview

열린 이슈를 전수 분석해 **이슈별 작업 계획을 댓글로 등록**하고, 승인 후 **의존 순서대로 전부 처리**하는 파이프라인. 핵심 원칙: **분석은 병렬, 수정은 순차. 같은 파일을 만지는 이슈는 반드시 순서를 정하고, 커밋 게이트는 테스트 exit code로만 판단한다.**

두 단계 요청으로 나뉘어 들어올 수 있다:
- "계획 댓글 달아줘" → Phase 1~2까지만 수행하고 멈춘다
- "전체 작업 진행해줘" → Phase 3~5 수행 (계획 댓글이 이미 있으면 재분석 생략)

## Phase 1: 이슈 수집 및 병렬 분석

- [ ] `git remote -v` — 올바른 저장소 확인
- [ ] `gh issue list --state open --json number,title,body` — 전수 조회
- [ ] 이전 점검 리포트(`.claude/health-reports/`)가 있으면 먼저 읽기 — 분석 비용 대폭 절감
- [ ] 연관 이슈끼리 2~3개씩 묶어 **Explore 서브에이전트로 병렬 분석** (코드 수정 금지·댓글 등록 금지 명시). 각 에이전트는 이슈별 댓글 초안을 정해진 구분자(`=== ISSUE N ===`)로 반환

## Phase 2: 계획 댓글 등록

이슈마다 아래 형식으로 댓글 등록 (`gh issue comment N --body-file`):

```
**처리 방향**: 핵심 접근 (파일:라인 근거)
**수정 대상**: 파일 목록
**작업 단계**: 3~5단계
**의존 관계**: 선행 이슈, 같은 파일을 수정하는 이슈
**예상 작업량**: S/M/L
```

- [ ] 마크다운 본문은 heredoc(`<<'EOF'`)으로 임시 파일에 쓰고 `--body-file`로 등록 (따옴표/백틱 이스케이프 사고 방지)
- [ ] 댓글 등록 후 **의존 그래프와 권장 작업 순서**를 사용자에게 보고
- [ ] 원래 요청이 계획까지면 여기서 **중단**. 처리 지시가 있을 때만 Phase 3 진행

## Phase 3: 실행 준비

- [ ] 작업 브랜치 생성 (예: `ralph-issues/1-13`)
- [ ] 상태 파일 `.claude/ralph-issues-state.local.json` 생성 — 이슈별 status/retries/commit 추적 (`.gitignore`에 `.claude/*.local.json` 포함 확인)
- [ ] 테스트 환경 구성 (venv + 의존성 + pytest). 테스트 인프라가 없으면 **인프라 도입 이슈를 0순위로 처리**
- [ ] 처리 순서 결정 원칙:
  1. 테스트 인프라 → 2. 최소 수정(워밍업) → 3. 의존 관계 순서(같은 코드를 만지는 이슈는 선행 이슈부터) → 4. 독립 이슈들 → 5. 광역 리팩토링(타입 도입 등 여러 모듈을 건드리는 것) → 6. 문서 동기화는 **맨 마지막** (기능이 확정돼야 재수정이 없다)

## Phase 4: 이슈별 처리 루프

각 이슈에 대해 반복:

1. **RED**: 버그/기능을 재현하는 실패 테스트 먼저 작성, 실패 확인 (`pytest` 직접 실행)
2. **GREEN**: 통과시키는 최소 수정
3. **커밋 게이트**: `./venv/bin/pytest; echo "EXIT=$?"` — **exit code 0 확인 후에만** `git add <명시적 경로> && git commit`. 커밋 메시지는 `{type}: {설명} (#{이슈번호})`, 한국어, Claude 서명 금지
4. **이슈 close**: `gh issue close N --comment` — 반영 내역 표 + 검증 결과 + 커밋 해시. **해시는 커밋 완료 후 `git log -1 --format=%h`로 확보한 실제 값**을 넣는다
5. **상태 파일 갱신**: status=completed, commit=해시
6. 실패 시: 1회 재시도 → 그래도 실패면 failed 기록 + 실패 댓글 후 다음 이슈로

## Phase 5: 마무리

- [ ] 전체 테스트 + **실제 파이프라인 E2E 실행** (DRY_RUN 등 부작용 없는 모드)으로 최종 검증
- [ ] 결과 요약표 출력 (이슈·상태·커밋, 완료/실패 수)
- [ ] 검증 불가 항목(예: 다른 OS 전용 수정)은 **명시적으로 한계 보고**
- [ ] 푸시/머지는 사용자가 명시 요청할 때만. 머지 후에도 테스트 1회 재실행 후 푸시

## Common Mistakes (실제 실행에서 발생한 것들)

| 실수 | 방지책 |
|------|--------|
| close 댓글에 `{HASH}` 플레이스홀더가 그대로 등록됨 | 커밋을 먼저 완료하고 `$(git log -1 --format=%h)` 또는 확인된 해시를 넣을 것. 등록 후 본문 검증 |
| `pytest \| tail`로 커밋 게이트 — 파이프가 exit code를 가려 **실패한 테스트가 커밋됨** | 게이트 판정은 파이프 없이 실행하거나 `; echo "EXIT=$?"`로 코드 확인. 사고 시 수정 후 `--amend` |
| 같은 파일을 수정하는 이슈를 임의 순서로 처리 | Phase 2에서 식별한 충돌 쌍은 반드시 순차 (예: 캐시 코드 #3→#8, 수집기 #5→#6) |
| 문서 동기화를 기능 구현 전에 처리 → 재수정 발생 | 문서 이슈는 항상 마지막 |
| 광역 타입 리팩토링을 먼저 해서 이후 이슈마다 충돌 | 여러 모듈을 건드리는 리팩토링은 버그 수정 완료 후 |
| 테스트에서 `import a.b as x`가 패키지 `__init__`의 동명 객체에 가려짐 | `importlib.import_module("a.b")` 사용 |
| 기존 분석/계획 댓글이 있는데 분석 댓글을 중복 등록 | 처리 시작 전 이슈 댓글 확인, 계획이 있으면 그대로 실행 |
| 알려진 버그의 "올바른 동작"을 인프라 도입 단계 테스트로 작성 → 처음부터 RED | 인프라 도입은 현재 동작의 green 베이스라인, 버그별 RED는 해당 이슈에서 추가 |

## Red Flags — 멈추고 다시 확인

- 커밋하려는데 테스트 exit code를 직접 확인하지 않았다
- close 댓글 본문에 변수/플레이스홀더가 남아 있다
- 다음 이슈가 방금 수정한 파일을 또 수정하는데 순서를 검토하지 않았다
- "이 이슈는 간단하니 테스트 없이" — 테스트 인프라가 있는 한 RED 먼저
